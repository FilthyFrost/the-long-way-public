## 执行方式（用户 2026-11-18 更新）

- 控制额度。按节点逐个完成系统：先做当前节点确实需要的最小共享基础，再把一个系统做到完整可玩、可验证、集成通过，保存本地提交和版本标签，然后才开始下一个系统。
- 同一时间只推进一个节点。节点内最多 2–3 个代理（一个实现，一到两个独立审查）。
- 每个节点结束时：全部门禁通过，本地提交，打本地标签 `v3-n<编号>-<名字>`，更新本文件，向用户汇报。额度随时可能用完，所以每个标签都是一个能运行的游戏。
- 不逐节点等用户确认；用户可以随时改顺序。只动本工程；只做本地提交，不推送，不对外发布；不买额度。
- 美术与质量目标不变。这台开发机没有独显，任何截图和时间都不是显卡实测。

### 每个节点通用的完成条件

1. `npm run check`、`npx vitest run`、`npm run build` 全部通过，现有测试一项不少。
2. 本节点新增：核心逻辑的单元与仿真测试；目录完整性测试（每一行内容都有模型、图标、中英文名和去向）；确定性测试（同一种子同一结果）；存档往返与旧存档读入测试。
3. 性能代理指标在本节点的预算内：在 Node 里量每步毫秒与分配；数出新增的绘制调用和三角形。写明数字。
4. 一个本节点的实机脚本（真的在游戏里走一遍这个系统）通过；冒烟组（`modcar_journey`、`modcar_save`）仍然通过。用 llvmpipe 软件渲染，只算功能验证。
5. 测试面板有本系统的页签，所有内容能直接调出来。
6. 画面自检：模型看板图和游戏内截图交给独立评审，对照 `specs/art/STYLE.md`；不达标就改。正式的画面与帧率验收要在目标硬件上做，这里一律写“未实测”。
7. 合并进 `feat/v3`，打标签，更新本文件：交付了什么、测试数字、留给后面节点的接口、已知缺口。
