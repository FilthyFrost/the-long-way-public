# LOOP v2：逐节点开发的规程

`loop/LOOP.md` 是单线规程，仍然有效；本文件规定 V3 怎么按节点推进、怎么用少量代理、怎么验收。方案见 `docs/V3/PLAN.md`，节点清单与各节点的验收条件见 `docs/V3/STATUS.md`。

2026-11-18 用户把执行方式从“大规模并行”改为“控制额度、逐节点闭环”，本文件按此重写。

## 1. 节奏

- 同一时间只推进一个节点。一个节点 = 一个系统做到完整可玩、可验证、集成通过。
- 共享基础按需做：N0 只做 N1 用得到的；之后每个节点需要新接缝时，在该节点的第一步里自己开，开得通用，后面的节点直接复用。
- 节点结束：门禁全过 → 本地提交 → 本地标签 `v3-n<编号>-<名字>` → 更新 `STATUS.md` → 向用户汇报。
- 节点内部分成几步，每一步合并后游戏都能运行。额度中途用完时，最近一次提交就是可运行的版本。
- 不逐节点等用户确认。

## 2. 角色与并行上限

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| 主会话（集成者） | 写任务书；合并；跑门禁；读截图做回归；更新进度；汇报 | 不把数量当质量；不虚报显卡实测 |
| 实现代理 | 一次一个任务包；只改任务书列出的文件；在指定的工作树和分支里提交 | 不改清单外的文件；不推送 |
| 审查代理 | 独立上下文，只读；找正确性、存档与确定性、性能方面的问题 | 不改代码 |
| 评审代理 | 只看截图和评分表，不看代码 | — |

- 节点内并行（用户 2026-11-18 晚要求：节点慢的时候用并行子代理加快，怎么拆由主会话定，注意额度）：
  1. 主会话先把各条线共用的最小接口写成代码并提交（纯核心的类型与函数、两条线交汇处的方法签名），各条线从这个提交分出。
  2. 两到四条实现线同时做，每条线有自己的工作树、分支和一张“只许改这些文件”的清单；共享的大文件（如 `ModGame.ts`）按段落划归属，不改别人的段落，不动已有的 import 行。
  3. 需要别的线改的东西不自己动手，写进报告的“需要其他线配合”。
  4. 各线只跑与自己有关的少数实机脚本，不重复做“改动前”基线（基线在 `STATUS.md`）；整组实机门禁由主会话在合并后跑一次。
  5. 合并后一到两位只读审查；发现的问题发回原实现代理修（保留它的上下文，比新开一个代理省时间也省额度）。
- 同时运行的代理一般不超过 4 个；本机 8 核，实机脚本吃满多核，同时跑的浏览器不超过 3 个。
- 不跨节点并行：下一个节点的实现不提前开工；主会话可以在等待时写下一个节点的设计和接口。

## 3. 分支与工作树

- 集成分支是 `feat/v3`，只做本地提交，不推送，不对外发布。只动这一个工程，`/workspace` 下的其他目录不读不写。
- 任务包在主会话建好的工作树里做：目录 `.claude/worktrees/<包名>`，分支 `v3/<包名>`，从当时的 `feat/v3` 分出。名字固定，所以被打断的任务包可以在原地接着做。
- 工作树里没有 `node_modules` 时先跑 `npm ci`（不要用软链接）。
- 实现代理每完成一小步就提交。接手一个已有分支时，先看 `git log feat/v3..HEAD` 和 `git status`，保留好的部分，从断点继续。
- 提交信息沿用仓库的写法：一句完整的英文句子说明做了什么，末尾加 `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`。

## 4. 任务书

每个任务包的任务书写在工作流的提示里，包含：

1. 目标：做完能看到什么。
2. 必读：方案的哪几节、哪几张代码地图（`docs/V3/maps/`）的哪几节、哪些现有文件。只列用得到的。
3. 只许改的文件 / 可以新建的目录。
4. 交付物：代码、测试、数据、模型、文档。
5. 验收：必须新增并通过的测试；必须仍然通过的现有测试；性能预算（毫秒、绘制调用、三角形、分配）。
6. 不做什么。
7. 交付说明的格式：提交列表、改了哪些文件、跑了哪些命令及结果、没做完的和发现的问题。

新系统的设计说明写在 `docs/V3/nodes/N<编号>-<名字>.md`：这个节点的数据表长什么样、新开了哪些接缝、留给后面节点的接口。只写这个节点的，不提前设计别的系统。

## 5. 代码规矩

- 纯逻辑放 `src/core`（不依赖 three 和 DOM），先写测试再写实现；画面与输入放 `src/game/modcar/v3/<系统>/`，入口是该目录的 `index.ts`，由游戏自动发现。
- 玩法逻辑确定性：不用 `Math.random` 和系统时间，只用种子哈希（`src/core/math/rng.ts`）。
- 内容是数据表：加一种动物、一条鱼、一道菜是加一行，不是加一段代码。
- 热路径不分配对象。新的可见内容走实例化或合批。（说明：系统计时每帧读几次 `performance.now()`，每次约 50 纳秒、引擎可能为返回值分配至多 16 字节；这是已接受的成本，“不分配”指系统自己的代码。）
- 新系统接进游戏只通过 N0 开的接缝；确实需要新接缝时在任务书里写明，由该节点的第一步统一开。
- 经典版（`classic.html`）和模型预览页要保持能编译、能运行。

## 6. 门禁

| 门禁 | 什么时候跑 | 内容 | 时间 |
| --- | --- | --- | --- |
| 快门禁 | 每次合并后 | `npm run check`；`npx vitest run` | 约 1 分钟 |
| 实机冒烟 | 动了主循环、玩家、存档、物品的合并之后 | `SHOTS_GL=llvmpipe node harness/shots/modcar_journey.mjs`、`modcar_save.mjs`，加上与改动相关的脚本 | 每个脚本几分钟 |
| 节点门禁 | 节点结束 | 快门禁 + 冒烟 + 本节点的实机脚本 + `npm run build` + 本节点的规格卡与机器人玩家 + 画面自检 | 十几分钟到几十分钟 |
| 目标硬件实测 | 有目标硬件时 | 基准路线，结果写进 `loop/perf/<日期>-<显卡>.json` | 需要用户的机器 |

- 实机脚本同一时间只跑一个，由主会话跑；实现代理需要时可以跑自己任务包的那一个，任务书里写明。
- 这台开发机没有独显。软件渲染的截图只用于功能和像素回归，不作为画面或性能的正式验收；任何报告都不得把它写成显卡实测。
- 会写入已跟踪文件的命令（`npm run measure`、`node harness/shots/run.mjs` 会改 `loop/metrics/*.json`）只由主会话运行。
- 实机脚本里不要用墙上时钟等结果（“等 0.4 秒看有没有 5 帧”在软件渲染下必然失败）；按帧数或游戏内时间等条件成立。

## 7. 性能契约

- 每个系统注册时申报每步的毫秒预算，游戏按系统计时。
- 交付说明里写明：Node 里量到的每步毫秒、新增的绘制调用数和三角形数。
- 超预算不是“以后再优化”，是不合并。
- 预算总表在 `docs/V3/PLAN.md` 的“性能工程”。

## 8. 停下的条件

额度用完、需要登录或权限、只能在目标硬件上做的验收。停下时保证：工作树里的改动已提交，`STATUS.md` 写明停在哪一步。
