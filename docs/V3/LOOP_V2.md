# LOOP v2：多个代理并行开发的规程

`loop/LOOP.md` 是单线规程，仍然有效；本文件在它之上规定多个代理并行时怎么分工、怎么合并、怎么验收。方案见 `docs/V3/PLAN.md`，共享接口见 `docs/V3/ARCHITECTURE.md`，任务包清单见 `docs/V3/WORKPACKAGES.md`。

## 1. 角色

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| 主会话（集成者） | 定共享接口与数据契约；写任务书；按依赖顺序合并；跑门禁；读截图做回归；记录进度 | 不把数量当质量；不虚报显卡实测 |
| 实现代理 | 一人一个任务包；只改任务书列出的文件；在自己的工作树和分支里提交 | 不改别人的文件；不改共享契约；不推送 |
| 审查代理 | 独立上下文，只读；从正确性、性能、确定性与存档兼容三个角度找问题 | 不改代码 |
| 评审代理 | 只看截图和评分表，不看代码 | — |
| 机器人玩家 | Node 里按固定策略跑的旅人、猎手、钓手、厨子 | — |

## 2. 分支与工作树

- 集成分支是 `feat/v3`，只做本地提交，不推送，不对外发布。
- 每个任务包在自己的 git 工作树里做，分支名 `v3/<包号>-<短名>`，从当时的 `feat/v3` 分出。
- 工作树里没有 `node_modules` 时先跑 `npm ci`（不要用软链接：几个工作树共用一份 Vite 缓存会互相打架）。
- 提交信息沿用仓库的写法：一句完整的英文句子说明做了什么，末尾加 `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`。
- 只动这一个工程。`/workspace` 下的其他目录不读不写。

## 3. 文件归属

- 每个任务包的任务书里有一张“只许改的文件”清单；清单以外的文件一律不改。需要改清单外的文件，停下来在交付说明里写明，由主会话决定。
- 共享文件在地基阶段（P0）开好注册接口，之后冻结：`src/game/modcar/ModGame.ts`、`player.ts`、`save.ts`、`entry.ts`、`devPanel.ts`、`src/core/modcar/items.ts`、`crafting.ts`。新系统通过 `docs/V3/ARCHITECTURE.md` 里的注册表接入。
- 共享契约（`src/core/v3/contracts/`）只有主会话能改。发现契约不够用，在交付说明里提出，不要自己加字段。
- 每个系统的内容表归该系统的任务包所有（`src/core/v3/content/<系统>.ts`）。

## 4. 任务书模板

每个任务包一份 `docs/V3/briefs/<包号>.md`：

1. 目标：一句话，做完能看到什么。
2. 背景与必读：方案的哪几节、哪几张代码地图（`docs/V3/maps/`）、哪些现有文件。
3. 只许改的文件 / 可以新建的目录。
4. 要用的共享接口与数据契约（列出类型名）。
5. 交付物：代码、测试、数据、文档各是什么。
6. 验收：必须新增并通过的测试；必须仍然通过的现有测试；性能预算（毫秒、绘制调用、三角形、分配）。
7. 不做什么：明确划在范围外的东西。
8. 交付说明的格式：分支名、提交列表、改了哪些文件、跑了哪些命令及结果、没做完的和发现的问题。

## 5. 一个任务包的流程

1. 实现：核心逻辑先写测试再写实现；`src/core` 不依赖 three 和 DOM；玩法逻辑确定性（不用 `Math.random` 和系统时间，只用种子哈希）。
2. 自检：`npm run check` 和 `npx vitest run`（全量 40 秒左右）。
3. 审查：三位审查代理各一个角度；确认的问题回给实现代理修；最多三轮。
4. 合并：主会话把分支合进 `feat/v3`（有冲突由主会话解决），然后跑快门禁。
5. 记录：`loop/reports/` 追加当天报告；`docs/V3/WORKPACKAGES.md` 更新状态。

连续三轮过不了门禁的任务包：标 `[需要人]` 或由主会话换做法重写任务书。

## 6. 门禁

| 门禁 | 什么时候跑 | 内容 | 时间 |
| --- | --- | --- | --- |
| 快门禁 | 每次合并后 | `npm run check`；`npx vitest run`（含核心纯度、目录完整性、性能代理指标） | 约 1 分钟 |
| 实机门禁 | 动了主循环、玩家、存档、渲染的合并之后；每一批结束时 | `harness/shots/modcar_journey.mjs`、`modcar_stress.mjs`、`modcar_save.mjs` 等实机脚本；相关截图组 | 每个脚本几分钟（软件渲染） |
| 全门禁 | 每个里程碑结束 | 快门禁 + 全部实机脚本 + 截图矩阵无报错 + 机器人玩家 + 确定性哈希 + 存档往返与迁移 | 几十分钟到几小时 |
| 画面评审 | 画面任务包合并前后 | 独立评审代理按 `specs/art/rubric.md` 打分；新旧同机位盲评 | — |
| 目标硬件实测 | 有目标硬件时 | 基准路线，结果写进 `loop/perf/<日期>-<显卡>.json` | 需要用户的机器 |

- 实机脚本和截图同一时间只跑一个（软件渲染会占满处理器）。实现代理默认不跑实机脚本，由主会话在集成时跑；任务书另有说明的除外。
- 这台开发机没有独显。软件渲染的截图只用于功能和像素回归，不作为画面或性能的正式验收；任何报告都不得把它写成显卡实测。
- 会写入已跟踪文件的命令（`npm run measure`、`node harness/shots/run.mjs` 会改 `loop/metrics/*.json`）只由主会话在集成时运行。

## 7. 性能契约

每个任务包在任务书里领一份预算（见 `docs/V3/PLAN.md` 的“性能工程”），并且：

- 新系统在注册时申报自己的毫秒预算；`SystemRegistry` 按系统计时。
- 新的可见内容必须走实例化或合批，交付说明里写明新增的绘制调用数和三角形数。
- 热路径不分配对象；给出一条在 Node 里量每步耗时和分配的测试。
- 超预算不是“以后再优化”，是不合并。

## 8. 一直迭代到做完

- 一个里程碑 = 若干批任务包。每批：排任务包 → 并行实现与审查 → 合并 → 门禁 → 记录。
- 里程碑评审：完整性检查（方案里这一里程碑承诺的每一条是否兑现）、机器人玩家报告、画面评审。发现的缺口变成下一批任务包。
- 待办清空且全门禁通过，里程碑才算完成；之后进入打磨循环，评审分数连续两轮提升不到 0.05 就停。
- 停下的条件：额度用完、需要登录或权限、只能在目标硬件上做的验收。
